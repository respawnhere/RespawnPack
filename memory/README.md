# RespawnPack: Memory layer

Operational recall, so the agent stops re-investigating solved problems. This is **distinct from `docs/DECISIONS.md`** (which is canonical *product/architecture* decisions): the memory layer holds **gotchas, infra facts, and learnings**, the "we hit this before, here's the fix" knowledge.

## The one rule that makes memory pay off
**Reading it is mandatory.** Memory that's written but never consulted is dead weight, the #1 failure mode of every memory system. So the discipline is baked into the roles: [`/debug`](../skills/debug/SKILL.md) **Step 0 queries memory before investigating**, and resolves close the loop by capturing back ([`/debug`](../skills/debug/SKILL.md) Step 5, [`/knowledge`](knowledge/SKILL.md)).

## What's stored
- **Knowledge graph**: entities + relations + observations (gotchas, infrastructure facts, compatibility constraints, hypotheses, and confirmed `rule:<slug>` project rules). Conventions: [`knowledge-graph.md`](knowledge-graph.md). An owner's correction travels the candidate gate and, when promoted `--as rule/<slug>`, is written into the project's versioned rules file the skills load as well as the graph, with `doctor` flagging a hand edit (G15).
- **Learnings ledger**: lighter, append-on-resolution lessons with confidence + source. Format: [`learnings.template.md`](learnings.template.md).
- **Candidate memories**: `/savepoint`'s automatic, evidence-backed captures — every failed/undetermined check and every operator-stated root-cause/fix pair. Tracked at `memory/candidates/<id>.json` + `memory/candidates/audit.jsonl` (`core/memory/candidates.js`), reviewed with `respawnpack memory candidates`. **A candidate is not a fact**: it is recallable only as an unverified lead until an explicit, audited `promote` writes it into the graph above (`memory/graph/<type>/<slug>.md`). **And a candidate must be a LEAD, not a copy of what the project already holds**: an automatic capture whose claim is already recorded in the graph, `docs/DECISIONS.md`, the removal registry or a requirement row is captured then rejected in the same run with the reason naming the record (or, for a matching graph entity with new evidence, folded into that entity as one dated observation and not minted at all); code and tests are not searched; a deliberate operator `--candidate` is never filtered, only annotated with any record it resembles. **Every verdict carries an author (G6)**: `promote` and `reject` require a non-null `--by "<who>"` as well as `--verified-by`/`--why`, refused when blank and never defaulted (a machine author like `savepoint` is valid); rejecting a candidate whose graph entity is still live either `--retract`s it under `memory/graph/_retracted/` with the reason or is refused naming the entity, never leaving it stranded; and `respawnpack memory candidates --ledger` names every integrity anomaly (verified-without-entity, entity-without-lineage, verdicts-without-author, retracted, open-older-than-sessions), which `doctor` carries one row per. See [`knowledge-graph.md`](knowledge-graph.md#candidates-a-lead-is-not-a-fact).
- **The register**: `docs/derived/LESSONS.md`, the human-readable projection of everything above. `savepoint --write` renders it — one row per VOUCHED entity promoted into `memory/graph/**` (its id, first observation, `promotedAt`, the `verifiedBy` that earned it, and the skills its `applies-to|skill:` relations name), then the count of leads in `memory/candidates/` still awaiting review — and `savepoint --verify` parses every number back out and compares it to those files, so a stale count is a `FAIL` rather than a plausible sentence. The register shows what the schema now carries (G7): an entity superseded by another's `supersedes|` relation renders `superseded by <id>` (the superseded file is never rewritten; a chain shows only the latest as current, a cycle is named); entities with no stated `verifiedBy` render in their own `## Unvouched` section, excluded from the verified table and count; and a `## Stale by horizon` list carries lessons whose `asOf` (default `promotedAt`) is older than `memory.staleHorizonDays` (default 180, `0` disables it) measured against the store's newest date, never the clock. The unvouched and stale counts are verified claims like the rest. It is a projection, never a source: nothing is decided or written there, and the promotion gate below is still the only door by which a new entity ENTERS the graph (D4's qualification rule adds a dated observation to an entity that already exists, on a `--write` run only, and never creates one; a `--verify` authors nothing in the graph and defers any such fold to the next `--write`). SessionStart cites it in one line, so a session is told the store exists instead of having to think to look — the failure this register was built for was thirteen candidates accumulating unreviewed across sessions because nothing ever mentioned them.
- **The inbound feedback channel (G16)**: `respawnpack feedback --export` packages the records a project holds ABOUT THE PACK (its pack-directed candidates, graph entities and decisions) without its operational detail, behind a mechanical redaction fence and an owner preview, and `respawnpack memory candidates import <file>` lands each on the dev side as a CANDIDATE, authored `import:<projectId>`, never a lesson. An import is a lead until a human promotes it, and its self-reported `packVersion` is verified against this checkout's known releases rather than trusted. What leaves, what never leaves, and how the receiver verifies are in [`knowledge-graph.md`](knowledge-graph.md#the-inbound-feedback-channel-g16-what-leaves-and-what-never-does). Host auto-memory notes and `.claude/rules/` files are out of scope: prose with no mechanical identity.
- **Why this repository's own `memory/candidates/` ships tracked**: intentional dogfood residue, a transparency artifact of the same class as `docs/derived/state/pairs.json` and `docs/derived/state/removals.json`. It is never copied into a target install; `install/_sources.js` never names `memory/candidates/`.

## Operational records (G17, decision 50)

Two records the spine does not own, for the operational class the field invented: what was DONE, and what BROKE. **The single-sourcing rule binds them**: each fact is owned by exactly one record, and every other record may only POINT at it by id.

- **The ops log** - `.respawnpack/ops-log.jsonl`, an append-only stream of actions, one JSON row per line sealed in a `prevDigest` chain (`{ at, by, action, result, refs, cycleId, prevDigest, digest }`). It OWNS an action and its result: a decision, a candidate claim or CONTINUITY's note may reference a row by its digest, none may restate its result. Written by the `log` verb and the savepoint (one row per writing run), read by a HANDOFF projection and `doctor`'s `ops-log:*` rows. **It is MACHINE-LOCAL** - under `.respawnpack/`, which the installer gitignores, so it never travels in a clone, the same durability class as the session baseline and the catches journal. A rewritten or spliced row breaks the chain and is refused as not append-only; a torn tail is reported and discarded only by `log --repair-tail`, which records the repair; a last-row rewrite with its digest recomputed is caught only once the next row seals it (disclosed limit). The append is serialised by an exclusive lock on `.respawnpack/ops-log.lock` (G17 R1) so two of the pack's own writers cannot splice the chain; that lock binds only the pack's writers - an outside editor appending by hand is not bound and can still break the chain, which `doctor`'s `ops-log:chain` then names - and `log --repair-tail` never re-seals a broken chain (that would launder a rewrite), only a torn tail.
- **The incident library** - `memory/incidents/<id>.json`, one authored claim each (`signature`, `cause`, `fix`, `status`, provenance, `logRefs`, `candidateId`). It OWNS an incident's signature, cause and fix. **TRACKED**, committed to the repository: an incident is project knowledge. `incident --new` writes the record AND mints one `root-cause-fix` candidate in the same call whose claim names the incident by id and NEVER carries the fix body - so the fix lives once, here, and a lesson promoted from that candidate cites the id (see [`knowledge-graph.md`](knowledge-graph.md)). The only edit a verb makes to an existing record is `incident --close` (`status`, `closedAt`, `closedBy`); signature, cause and fix are never rewritten.

A lesson is still owned by the graph and reached only through the audited promotion gate: until then an incident's fix is a claim with provenance, not a lesson.

## What this is not
The memory layer is not a code index. "What does the code say right now" is answered by Claude Code's own search (Grep, Glob, agentic reading), and "what exists and where it lives" is answered by the docs spine's feature-page-flow matrix. Memory holds what the code cannot say on its own: decisions, constraints, gotchas, learnings, and why something is the way it is. A pre-built code index would go stale on every commit; this layer exists for knowledge that has no other home.

The code-structure question now has a recommended companion: Graphify, wrapped as a pinned external tool via the `ops/mcp/graphify` skill, for calls, imports, and blast-radius queries over an AST-derived graph. The boundary still stands: Graphify holds what the code IS, this layer holds WHY.

## One backend, and the host mirror
File + grep over the markdown entity files is the one backend the pack ships: `memory/graph/<type>/<slug>.md` is the source of truth, and `/debug`, `/knowledge` and `/skill-guard` read it by grep. The optional `respawn-memory` engine (a PGLite + pgvector MCP server) was retired with `--with-memory` (decision 33, 2026-10-09): it returned an empty recall after every reinstall until a manual sync, and the host now carries a mirror instead. A lesson may also be bound to the revision of the world it was true in (G8: a commit, a document digest or an estate serial, written by `promote --world`), so the register and `doctor` flag it "behind" and prompt a re-verify once the current revision moves past it, with the honest degrade that the pack cannot read a live estate over the network. Canonical schema statement: [`knowledge-graph.md`](knowledge-graph.md#one-schema-one-backend).

**The host auto-memory mirror.** When a lead is promoted (`respawnpack memory candidates promote <id> --as <type>/<slug> --verified-by "<what proved it>"`), the graph entity is written AND one line is mirrored into Claude Code's own auto memory `MEMORY.md` (`~/.claude/projects/<encoded>/memory/MEMORY.md`, or the `autoMemoryDirectory` setting when set, or `RESPAWNPACK_AUTO_MEMORY_DIR` for tests), so a fresh session's index points at the lesson without reading the project. `reject` removes the mirror. The graph entity is the record; the mirror is a projection that can be absent (no auto memory for this project), withheld (the index is at the host's 200-line / 25 KB cap) or stale, and the promotion's verdict stays on the graph write. The pack only ever touches its own files (named `respawnpack-*`), never a line a human or the host wrote; nothing in `memory/.index/` (the retired engine's database) is deleted by the pack. The host does not document recognising files another program wrote beyond their being plain Markdown, so the mirror is a convention the docs permit, not a contract.

## The write/read loop
```
/debug Step 0:  search memory for the symptom  ──►  start from the recorded root cause + fix (if found)
        Step 5:  on resolution, capture symptom → root cause → fix  ──►  feeds the next Step 0
/knowledge:      query ("what do we know about X") OR capture a gotcha/learning
/savepoint:      (optional) prompt to capture any uncaptured gotcha from the session
```

## Boundary with the spine
- A **product/architecture decision or removal** → `docs/DECISIONS.md` (canonical, human-authored).
- An **operational gotcha / infra fact / learning** → here (the graph/ledger).
- When in doubt: would a *generator* need it (then DECISIONS) or would a *debugger* need it (then memory)?
