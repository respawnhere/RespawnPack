# RespawnPack: Governance / hooks pack

The safety layer most solo setups skip. Fifteen hooks, written in **Node** (no `jq`, no bash/PowerShell branching in the hook logic; tested in CI on Windows and Linux, macOS expected but unverified, as long as `node` + `git` are on PATH). Source of the spec: Claude Code hooks docs (PreToolUse denies via `hookSpecificOutput.permissionDecision` and can rewrite the tool input via `hookSpecificOutput.updatedInput`; **model-visible** context injection via `hookSpecificOutput.additionalContext`, supported by SessionStart, Setup, SubagentStart, UserPromptSubmit, UserPromptExpansion, PreToolUse, PostToolUse, PostToolUseFailure, PostToolBatch, Stop and SubagentStop; Stop blocks via top-level `decision`; `stop_hook_active` guards loops; `${CLAUDE_PROJECT_DIR}` and `transcript_path` are provided).

⛔ **Two corrections this table used to get wrong, both load-bearing.** **`PreCompact` has NO `additionalContext` channel**: it accepts a top-level `decision`/`reason` and nothing else. A hook that emits `hookSpecificOutput` there is rejected by the runtime, so its message is never delivered; that is exactly what happened to `precompact-ledger-nudge.js` (DOGFOOD.md DF-002). And **`systemMessage` is user-visible only**: it is *not* added to the model's context, so a hook that speaks only on it is a desktop notification, never agent guidance. The **PreCompact** correction is pinned by the contract table in `hooks/_harness.mjs` and asserted for every hook. The **audience** correction is not, and cannot be from that table: `systemMessage` is a universal field there, so the table has no way to express "user-visible only"; that half is enforced by reading the hook, not by a fence by `hooks/hooks.test.mjs`.

**Eleven shared modules in this directory are not hooks** (the directory also holds test files and `_harness.mjs`; "eleven" is the set the counts fence pins, every one of them reached by a hook `require()` since P1-E-1d, not the count of non-hook FILES). `_contracts.js` (**the ONE typed-contract declaration**, read by `_boot.js` at runtime AND by `kernel/lib/modhealth.js` cross-tree for `doctor`, one object, not two lists that agree until one moves. `hooks/` is the only direction that resolves, since the kernel can require from here and the hooks cannot require from the kernel. It is a **protected, load-bearing contract source**, *not* an irreducible one: `_boot.need()` catches its failure and the hook degrades. This file said "irreducible" until it was checked on a real installed target, and the error was load-bearing: `BOOT_BOUNDARY` is what the degradation matrix skips, so the false claim excused the contract source from the sweep that proves it degrades. `_boot.js` carries the smallest possible bootstrap-interface check on it, the two members `_boot` itself calls, `CONTRACTS` and `validate`, because a contract source cannot answer questions about the machinery the answering is made of; everything else it declares is validated by the ordinary self-check), `_boot.js` (**the irreducible hook bootstrap boundary, and the only file in it**: every hook with shared dependencies enters through it, so a module that will not load degrades the hook to its declared posture (a safety-critical PreToolUse guard DENIES, SessionStart emits valid event output saying state is unavailable and claims are withheld, an advisory hook says why on stderr) instead of dying with a raw stack. A nonzero exit from a PreToolUse hook is a *non-blocking* error, so a hook that crashes is a guard that is not there. A defect in `_boot.js` itself is a raw crash, exactly as `respawnpack.js`/`outcome.js`/`modhealth.js` are for the kernel, and it is the one dependency for which `doctor` still says a hook "dies at its first invocation"), `_runtime.js` (ephemeral session-state kernel: SessionStart baselines, session-delta detection, stop-decision records, the interaction contract, durable-state freshness, compaction handoffs), `_cmd.js` (structure-aware git-command classification for push-guard and secret-scan), `_manifest.js` (the source-input digest manifest, shared with the state compiler), `_artifact.js` (the ONE production acceptance boundary: absent / transiently unavailable / unreadable / malformed / unsupported-version / structurally invalid are six distinct answers, and it decides whether a requirements or goal document may be consumed at all; the kernel requires it from here because the hooks cannot require from the kernel), `_shell.js` (the quote-aware structural shell parser: segments, tokens with their quoted values, `cd`/`export` state, `env`, constant `-c` wrappers, statically extractable `$(…)`/backtick spans, and an explicit *unsupported* verdict for anything it does not model. Reading a substitution span is not modelling it: the span stays *unsupported*, because knowing what runs inside `$(cat list.txt)` says nothing about what its output becomes in the command around it), `_git-effect.js` (what a git subcommand would do to the index, with pathspecs normalised into repository coordinates) `_index-lease.js` (git-index identity, semantic staged entries, exclusive writer leases) and `_posture.js` (**the ONE reader of the project's declared posture**, ADR-003's `light`/`standard`/`strict` and its per-rule overrides: `resolve(projectDir)` answers DECLARED, DEFAULTED, UNREADABLE or INVALID, and all but the first resolve to `strict`, because a policy that could not be read is never the loosest policy. Its resolver table has **no key** for any rule the anti-drift core fixes, so an override naming one is refused rather than ignored. `index-guard.js` binds it through `_boot.need`, and `kernel/lib/modhealth.js` reaches it cross-tree for `doctor`'s posture row) and `_exceptions.js` (**the ONE reader of the project's declared exceptions**, P1-E-1a: one tracked `exceptions` list in `respawnpack.config.json` whose every entry names a SUBJECT and never a verdict. A `path` glob, a `fingerprint` of the matched text, a `command` fingerprint, or an `item` id, and only the kinds the named rule actually computes. That is the line between this grammar and `posture.overrides`: an override moves a rule for every subject and is refused on the fixed set, while an exception carves out one reviewed subject, so it is accepted on any rule that has a subject notion, the security column included. `resolve(projectDir)` answers DECLARED, DEFAULTED, UNREADABLE or INVALID, and all but the first lift nothing, because an allowance that could not be read is never granted; an INVALID list is refused WHOLE rather than partly honoured, and an expired entry is kept in the list, matches nothing, and is counted by `doctor`. `shell-guard.js`, `push-guard.js`, `worktree-guard.js` and `index-guard.js` bind it through `_boot.need` (P1-E-1d) and `kernel/respawnpack.js` reaches it cross-tree for `doctor`'s `exceptions` row) are the shared modules in this directory. All eleven are what the hooks `require`, and they install alongside the hooks because a hook without them cannot load; they are excluded from the "fifteen" count because a library is not a governance hook. The set is fenced against the installer, the uninstaller and the manual copy command below by `counts-fence.test.mjs`, so a new shared module cannot be added in one place and forgotten in the others.

An index whose staged state cannot be inspected, or a wave counter that cannot be read, is **denied**, not assumed clean or empty. **Every** visible index mutation takes the writer lease for its target index, including an agent's own worktree; worktrees stay uncontended because their index *identities* differ, not because they are exempt. Git invoked from inside an arbitrary program (a package script, a Node/Python process, a compiled binary) is not visible to a `PreToolUse` hook at all. This hook does not police `git config`, `git remote` or `git clean`, which change configuration or untracked files rather than the index. |

**The posture key, and the one module that reads it.** `respawnpack.config.json` may carry a top-level `posture` block (`{profile, overrides}`) declaring how rigid this pack is on this project: `light`, `standard` or `strict`, with `strict` defined as exactly what 0.3.0 does (ADR-003). `_posture.js` is the ONE reader, and it lives here for the reason `_contracts.js` and `_artifact.js` already give: the kernel can require from `hooks/`, and `hooks/` cannot require from the kernel, whose path differs between this repo and an installed target. It answers with the profile, the declared per-rule overrides, and the SOURCE that produced them, which is four distinct facts rather than two. DECLARED is a founder who wrote one. DEFAULTED is a project that did not, resolving to `strict`, which is the migration guarantee: a target that says nothing keeps today's behaviour exactly. UNREADABLE is a config that could not be parsed and INVALID is a posture that is declared and wrong (an unknown profile, an override with no reason, an override naming a rule the anti-drift core fixes). Both of those fail closed to `strict` and say so in one line, because a policy that could not be read is never the loosest policy, and an override on a fixed rule is REFUSED rather than quietly discarded. The resolver carries no key for a fixed rule at all, so asking for one is unavailable rather than merely denied. `_posture.js` is the tenth of the eleven shared modules listed above, and the installer places it beside the others; the kernel additionally reaches it cross-tree for `doctor`'s `posture` row. **Eleven rules read it, across eight hooks.** `index-guard` asks about its four switchable rules (`editor-containment`, `no-bash`, `unmodelled`, `writer-lease`); `push-guard` about `push-guard:tier1`; `stop-savepoint` about `stop-savepoint:block`; `precompact-ledger-nudge` about `precompact:block`; `docker-session-tag` about its compose/chained advisory (`docker-session-tag:advise`); `mcp-reaper` about the whole of itself (rule id `mcp-reaper`); `spawn-guard` about `spawn-guard:ceiling` (P1-I-1); and `websearch-freshness` about the whole of itself (rule id `websearch-freshness`, P1-I-1). Each is a plain `require('./_posture.js')` (`spawn-guard` and `websearch-freshness` reach it through `boot.need`) resolved once per invocation, beside that hook's own marker check where it has one: `spawn-guard`'s is `.strict`, not `.off`, and only ever tightens a resolved verdict, never loosens one; `websearch-freshness` carries no marker at all, so it resolves at the first point in `check()` the rule could have anything to say. See their table rows above. `docker-session-tag`'s label/name rewrite is deliberately NOT among them: it is fixed on in every posture (anti-drift item 26) and carries no key in the resolver at all.

## Declaring an exception

`respawnpack.config.json` may also carry a top-level `exceptions` array: subject-scoped allowances for a guard that would otherwise deny. It is read by `_exceptions.js` (P1-E-1a, one of the eleven shared modules above), through a memoised `ctx.exceptions` getter beside `profile` (see "The `check(ctx)` contract" below). An exception names a SUBJECT it lifts, never a verdict it changes: the line between this grammar and `posture.overrides` above. An override moves a rule for every subject and is refused on the ids the anti-drift core fixes; an exception carves out one reviewed subject and leaves the rule denying everything else, so it is accepted even on the security column. Anti-drift item 25 still holds: the rule still fires on every OTHER subject, and `respawnpack.config.json` is already in `index-guard`'s `CONTROL_PLANE`, so a subagent cannot write itself one. ADR-004 (a development record) is the decision record for this grammar, the same way ADR-003 is for `posture`.

```json
{
  "exceptions": [
    {
      "id": "aws-doc-example-key",
      "rule": "secret-scan",
      "match": { "fingerprint": "sha256:<64 lowercase hex, copied from the deny>", "path": "docs/aws-setup.md" },
      "reason": "the AWS documentation example key, quoted in the setup guide",
      "declaredBy": "owner",
      "declaredAt": "2026-09-03",
      "expires": "2027-03-01"
    }
  ]
}
```

`id` is the string the lift is reported under. `rule` is the guard's id. `match` carries one or more of `path` (a glob), `fingerprint` (`sha256:` plus 64 lowercase hex, the exact string a deny prints), `command` or `item`, whichever kinds the named rule accepts, and every declared key must match: `{fingerprint, path}` means this line in this file, never this line anywhere. `reason` is required; `declaredBy` and `expires` are optional and are echoed back on the lift. An entry with no `reason`, an unknown `rule`, a subject kind the rule does not have, or a malformed date refuses the WHOLE list, not just that one entry, and the guard that would have consulted it says so in its deny reason.

**Six rules in `EXCEPTION_RULES` (`hooks/_exceptions.js`) are wired to a guard today; a seventh carries a subject kind with no consumer yet.** Full detail for each lives beside its own hook below ("Using push-guard", "Using shell-guard", "Using worktree-guard", "index-guard's rules, and which posture moves them", and the `secret-scan.js`/`injection-scan.js` table rows above); this is the index:

| Rule id | Subject kind(s) | What it lifts |
|---|---|---|
| `secret-scan` | `fingerprint` + `path` | one added line, in one file (P1-E-1b) |
| `injection-scan` | `path` | one `Read` hit on one project document; `WebFetch`/`WebSearch`/`Agent`/`Task` have no project path to except (P1-E-1c) |
| `shell-guard:catastrophe` | `command` | one command line, fingerprint over quoted-spans-blanked text (P1-E-1d) |
| `push-guard:tier2` | `command` | one command line; tier 1 has no subject notion and can never be excepted (P1-E-1d) |
| `worktree-guard` | `path`, relative to the **main checkout's root** | one path glob, covering every linked worktree of the repository (P1-E-1d) |
| `index-guard:unmodelled` | `command` | one command line; the other six `index-guard` rules (three switchable, three anti-drift-fixed) can never be excepted (P1-E-1d) |
| `readiness` | `item` | declared in the grammar and the schema; no hook asks `allowed()` about it yet |

Every wired rule prints the same sentence on a lift, in `systemMessage` and `hookSpecificOutput.additionalContext` alike: `🔓 allowed by exception <id> (<rule>): <reason>`, with the declarer and the expiry appended when present. An INVALID list refuses the whole declaration and is said out loud on the next deny from any of these six; a DEFAULTED or UNREADABLE one leaves the refusal exactly as it always was, so an unconfigured or unreadable project's decisions stay byte-identical to today's.

For `secret-scan`, the first guard this grammar reached, the subject is `{path, fingerprint}`: the file from the diff's `+++ b/` header, and `fingerprint()` of the added line itself, whitespace-normalised so a reformat does not silently expire the declaration. A HIGH hit that is not lifted is still named in the deny with its own path and fingerprint, so there is always something to paste into `match`. When every HIGH hit in a commit or push is lifted, the operation proceeds and the hook still speaks: `systemMessage` (the founder) and `hookSpecificOutput.additionalContext` (the model) both carry a line per lift, in this shape:

```
🔓 allowed by exception aws-doc-example-key (secret-scan): the AWS documentation example key, quoted in the setup guide (declared by owner, expires 2027-03-01)
```

When only some of a commit's HIGH hits are lifted, the operation still denies, naming only what still blocks and noting what was already lifted, so the founder is not asked to re-review a line already excepted. Neither a truncated scan (`RESPAWNPACK_SECRET_SCAN_MAX_COMMITS`) nor an uninspectable range can be lifted by any exception: both mean the guard could not establish an answer at all, and "could not look" has no subject to except. The `pre-push` git shim tells the identical story on stderr, exiting 0 only when every hit was lifted, and 1 the moment even one is not.

## The `check(ctx)` contract

Every `PreToolUse` hook in the table above has **two entry points and one decision** (P4-T-15a). It still runs standalone (`node .claude/hooks/<hook>.js`, stdin in, one JSON document out, exit 0), and that path is what `settings.snippet.json` wires today. Underneath it, the whole policy is a pure function:

```js
module.exports = { check, context };

check(ctx) -> verdict | null        // the hook's protocol output AS DATA, or "nothing to say"
context(input) -> ctx               // builds the ctx from parsed stdin + the environment
```

`ctx` is `{ input, projectDir, workDir, principal, git, profile }`:

- **`input`**: the parsed hook JSON, exactly as it arrived on stdin.
- **`projectDir`**: the project root this hook resolves state against. It is **not one definition across the nine**: `index-guard` and `spawn-guard` take `_runtime.projectRoot(input)`, the rest take `CLAUDE_PROJECT_DIR || cwd`, and `worktree-guard` deliberately walks up from where the *session sits* rather than from `input.cwd`. Each `context()` reproduces its own hook's resolution, unchanged. Reconciling them is a decision for the dispatcher (P4-T-15b), not something a refactor was allowed to make quietly.
- **`workDir`**: the tool call's working directory (`input.cwd`), falling back to `projectDir`. `secret-scan` scans this one; `index-guard` compares its index identity against the project's.
- **`principal`**: `_index-lease.principal(input)` for `index-guard`, which is the only check that has a principal; `null` elsewhere.
- **`git`**: a **memoised** git runner bound to one repository, or `null` for a check that runs no git. Only `secret-scan` has one today: identical `(args, absenceIsExpected)` pairs inside one decision run git once, and the first failure is recorded on the runner as `git.failure` rather than in a module-level variable. That relocation is the point: module state is correct for one process per hook and wrong the moment one process answers for several checks, where the second scan would otherwise inherit the first's "could not be inspected" and block a clean push on it.
- **`profile`**: the resolved posture (`_posture.resolve(projectDir)`) for the five checks that consult one: `index-guard`, `push-guard`, `docker-session-tag`, `spawn-guard` and `websearch-freshness` (the last two since P1-I-1). It is **`null` for the other four, on purpose.** `lockdown`, `worktree-guard`, `shell-guard:catastrophe` and `secret-scan` are ids the anti-drift core fixes in every posture, and a rule that has nothing to ask cannot be answered differently tomorrow. Where `profile` is real it is a **lazy getter that memoises**, so the one read of `respawnpack.config.json` still happens at the exact point in the pass the rule was written at, never earlier, and never twice.
- **`exceptions`**: the resolved declaration (`_exceptions.resolve(projectDir)`) for the checks that ask whether the founder has already reviewed the SUBJECT in front of them: `shell-guard`, `push-guard`, `worktree-guard` and `index-guard` (P1-E-1d). Absent on every other check, and that absence is load-bearing: a check with no `exceptions` getter is a check that consults no declaration, and neither this contract nor the dispatcher invents one for it. Like `profile` it is a **lazy getter that memoises**, and it is a *separate* getter rather than a second field on the same resolution, because a posture answers "what verdict does this rule have" and an exception answers "has the founder named this subject", two questions whose fail-closed directions differ (an unreadable posture resolves to the strictest profile; an unreadable or refused exception list lifts nothing).

Two properties the fences in `hooks/hooks.test.mjs` hold:

- **Both entry points emit the same document.** Each hook is replayed through the standalone process and through `check(ctx)` on identical stdin in identical environments, and the two documents are compared. Three states per check: a call the guard allows, one it refuses, and one whose facts it could not establish.
- **`check(ctx)` is pure.** It writes nothing to stdout and exits no process, measured by replacing `process.stdout.write` and `process.exit` with recorders around every call, not read off the source. **File writes are not a purity violation**: `spawn-guard`'s counter and wave ledger, `push-guard`'s consumed marker and `index-guard`'s writer lease *are* the behaviour those hooks are for.

`index-guard` reaches its answer by throwing rather than returning, and that is deliberate: `emitDeny`, `deny` and `finish` are called from inside loops and from inside `ruled()`, on the promise that the call never returns. They throw a `Halt` carrying the verdict, and `check()` is the only frame that catches it; anything that is not a `Halt` is re-thrown, so `_boot`'s last-resort net still sees real defects.

**What this is for.** `hooks/dispatch.js` (P4-T-15b) is the consumer, and it has landed. See the next section.

## `dispatch.js`: one process per PreToolUse registration group

`hooks/dispatch.js` is **not a governance hook.** It enforces nothing, carries no rule id, has no row in ADR-003's table and no entry in `install/_settings-manifest.js`'s `RULES_BY_HOOK`; `counts-fence.test.mjs` excludes it from the hook count by name, with that reason, because there are still fifteen guards. It is the entry point that runs them: `node ${CLAUDE_PROJECT_DIR}/.claude/hooks/dispatch.js PreToolUse <group> --covers <the guards, in order>` reads stdin once, resolves the posture, and the project's declared exceptions, once per distinct project root, calls each check's pure `check(ctx)` in a declared order, and merges the verdicts into one document.

**Two groups, and the declared order is the snippet's own.**

| Group | Matcher | Declared order |
|---|---|---|
| `edit` | `Edit\|Write\|MultiEdit\|NotebookEdit` | `lockdown.js` → `worktree-guard.js` → `index-guard.js` |
| `bash` | `Bash` | `push-guard.js` → `index-guard.js` → `shell-guard.js` → `docker-session-tag.js` |

The order is the order `hooks/settings.snippet.json` already registers these hooks in, so a founder reading their own `settings.json` can see it and a target flipping to `strict` does not change which reason it reads first. It cannot change *which* decision comes out; see the merge rule.

**The merge rule: most restrictive wins, order-independent for the decision.**

- **Decision**: the minimum of `deny` < `ask` < `allow` across every check that emitted one. A `deny` from any check beats an `allow`, an `ask` or an `updatedInput` from any other **regardless of declaration order**; a decision word this table does not know cannot be proved less restrictive than a deny, so it ranks with `deny` and is passed through verbatim rather than translated.
- **Reason**: every `permissionDecisionReason` at the winning rank, in declared order. Two guards that both refuse have two things to say, and dropping one hides the second refusal until the first is fixed.
- **`additionalContext` and `systemMessage`**: concatenated in declared order, deduplicated.
- **`updatedInput`**: carried only when nothing denied and nothing asked, because the tool does not run otherwise. At most one check per group may rewrite, fenced in `install/install.test.mjs`; `docker-session-tag`'s label splice is the only one today and it is last.
- **Anything else** a check emits is passed through unchanged rather than swallowed, so a check that invents a channel fails `_harness.mjs`'s `CONTRACT` fence loudly instead of going quiet the way DF-002 did.

**The registration names the guards it runs, and that is load-bearing twice over.** Measured before the `--covers` list existed: `doctor` on a healthy dispatching target reported `hook:lockdown.js`, `hook:worktree-guard.js`, `hook:push-guard.js`, `hook:shell-guard.js` and `hook:docker-session-tag.js` at `SILENTLY INACTIVE`, each carrying doctor's own detail:

```
on disk and valid but NOT wired in .claude/settings.json — it will never run
```

The whole report went from PASS to CANNOT_DETERMINE, and every one of those rows was false: the guards run, in one process, through the dispatcher. `doctor` decides "wired" by reading `settings.json` for a command that names the hook, and its own wiring reader keeps a raw-JSON substring fallback "so a spelling this regex does not know still counts as wired rather than being called silently inactive"; naming the guards is that spelling. It also makes the entry readable: a founder sees which guards one line runs, in the declared order. **The list can never shorten the guard set.** `GROUPS` in `dispatch.js` decides; a disagreement is reported on stderr and never obeyed, because a settings string that could drop `shell-guard` would be a one-line way past the security column. A profile that does not wire the dispatcher does not receive the *file* either, for the same reason: an unwired hook on disk is a `SILENTLY INACTIVE` row and a red report.

**Every check sees the original input.** A rewrite from one check is not fed to the checks after it, and a deny is computed against the input the host actually asked about. That is what the four parallel processes did, and it keeps a rewrite from becoming a channel that walks a command past the guards declared after it. The cost is that a rewrite is judged by nobody, so a rewriting check has to be safe on its own.

**The degradation posture is per group, not per hook (anti-drift item 27).** `boot.arm('deny')` fires literally, before any check is required. The posture is then recomputed as the most conservative among the checks the group is about to run and only re-armed if the group is genuinely quieter; both shipped groups compute `deny`, and item 27's own four names (`index-guard`, `push-guard`, `secret-scan`, `shell-guard`) are fenced to `deny` in the dispatcher's `CHECKS` table against each hook's own `boot.arm()` literal. **The cost, stated:** this is a single point of failure for a whole group. One check whose machinery will not load takes the group's answer to `deny`, where the multi-hook wiring would have denied on that hook alone. Strictly more conservative, never less, and the reason `strict` keeps the multi-hook wiring and the installer records which of the two it laid.

**What it does not cover, and why.**

- **`secret-scan`'s two Bash registrations stay two separate entries** with their own `if` rules, in every profile (anti-drift item 29: one permission rule per entry, never deduplicated). Folding them in would delete the host-side filter and hand `secret-scan` every Bash command instead of the two spellings it is registered for, which is a widening of a security scan decided by a wiring change. So a dispatched `git commit` is **2 processes, not 1**.
- **The one-hook groups stay as they are**: `spawn-guard` at `Agent|Task`, `websearch-freshness` at `WebSearch`. They are already exactly one command.
- **`strict` keeps the multi-hook wiring.** ADR-003 defines `strict` as exactly what 0.3.0 does and anti-drift item 35 makes that mechanical through P3-N-2's byte-identical freeze test, so the dispatcher is composed into `light` and `standard` only. A target that declares no posture keeps four processes per Bash call until it declares one. `.respawnpack/install-receipt.json` records `settingsWiring`, and the retirement record makes the flip reversible in both directions.

**Measured on a Windows 11 dev box, two windows, median of 15 parallel-fired runs each** (two warm-ups discarded, one throwaway git fixture, the same method as the hooks-and-install audit §4b). The box was running other work, so two windows are reported rather than one: the absolute milliseconds move with load and the process counts and ratios do not.

| Event | Before (busy · quiet) | After (busy · quiet) |
|---|---|---|
| Bash `PreToolUse`, plain command | 4 processes, 347 · 235 ms | **1 process, 212 · 171 ms** |
| Bash `PreToolUse`, `git commit` | 5 processes, 597 · 451 ms | **2 processes, 513 · 403 ms** |
| Edit `PreToolUse` | 3 processes, 294 · 233 ms | **1 process, 203 · 166 ms** |

The audit's own targets (60 ms, 180 ms and 75 ms) were set against an idle box with a 33.5 ms process floor, and this box's floor is nowhere near that. They are **not** met, and nothing in this pack claims they are. What is met is the process reduction those targets were derived from, less `secret-scan`'s registration, which stays separate on purpose.

Every hook it calls stays runnable standalone, and `hooks/hooks.test.mjs` replays the whole PreToolUse fixture set through both entry points and compares the documents.

## Install (manual, the Phase-6 installer automates this)
1. Copy the scripts into the target repo's `.claude/hooks/`:
   ```
   cp hooks/{_contracts,_boot,_runtime,_cmd,_manifest,_artifact,_shell,_git-effect,_index-lease,_posture,_exceptions,lockdown,worktree-guard,index-guard,secret-scan,stop-savepoint,push-guard,shell-guard,spawn-guard,websearch-freshness,injection-scan,context-monitor,precompact-ledger-nudge,session-routing-nudge,mcp-reaper,docker-session-tag,dispatch}.js  <repo>/.claude/hooks/
   ```
   `_contracts.js`, `_boot.js`, `_runtime.js`, `_cmd.js`, `_manifest.js`, `_artifact.js`, `_shell.js`, `_git-effect.js`, `_index-lease.js`, `_posture.js` and `_exceptions.js` are the shared modules; copy all eleven or the target is incomplete. Every one of them is required by a hook, so a missing one is a hook that cannot load. `_posture.js` joined that require graph when `index-guard.js` began resolving its rules through it, and `_exceptions.js` joined it at P1-E-1d, when `shell-guard.js`, `push-guard.js`, `worktree-guard.js` and `index-guard.js` began asking whether the founder had declared the subject in front of them. The state kernel also reads both cross-tree, for `doctor`'s posture and `exceptions` rows.
   `dispatch.js` is copied by every profile and wired by two: it is the entry point that runs the `PreToolUse` guards in one process, and `strict` does not register it (see [`dispatch.js`: one process per PreToolUse registration group](#dispatchjs-one-process-per-pretooluse-registration-group)). It is not one of the fifteen governance hooks and enforces nothing of its own.
2. Merge [`settings.snippet.json`](settings.snippet.json) into `<repo>/.claude/settings.json` (hooks accumulate across user/project settings; the snippet is additive; `permissions.allow` unions in on an exact-string match, read-only commands only, and never removes an entry already there). Drop the `Stop` block if you don't want the savepoint nudge: it is opt-in, fires on **session delta**, and depends on the `SessionStart` hook having recorded this session's baseline, so keep both wired together or the `Stop` block stays quiet.
   **The snippet is the `strict` column of a profile manifest, not the only set the installer lays.** `install.js` composes the registration set for the posture the target declares (ADR-003), through `install/_settings-manifest.js`. Under `strict` (and under a `DEFAULTED`, `UNREADABLE` or `INVALID` declaration, all three of which resolve to `strict`), the composed set is this file, byte for byte: 13 groups, 22 entries. Under `light` the two `mcp-reaper` registrations are omitted, because every rule that hook carries reads `off` in that column, so the wiring only existed to start a process that reads the config and exits. `standard` composes the same 22 entries as `strict`, since no hook is wholly `off` there. An entry is dropped only when **every** rule its hook carries is `off`; a hook with one fixed rule left (which is most of them) stays wired in every profile and self-disables from the inside. A hand merge of this file gives you the `strict` set, which is the safe one to hand-merge.
   **A second projection decides the wiring, not the guards.** Under `light` and `standard` the two fully-covered `PreToolUse` groups are each composed as one `dispatch.js` registration instead of three and four separate ones (same guards, same declared order, one Node process), so those profiles compose 15 and 17 entries rather than 22. Under `strict` they are not, because that profile is defined as today's behaviour and its composed bytes are pinned (anti-drift item 35). The two projections are kept in separate lists all the way into the receipt, so a wiring change never reads as a guard being switched off.
   **Deleting an entry sticks when the installer placed it.** `install.js` records the `(event, matcher, command, if)` tuples it merged in `.respawnpack/install-receipt.json`; a tuple named there and absent from `settings.json` is treated as deliberately removed and is never re-added, so `push-guard`'s own "delete the entry to disable me" advice now holds across upgrades. A tuple the record has never seen is new in this pack version and is added as before. See [`install/README.md`](../install/README.md#the-settings-merge-remembers-what-it-placed). A hand merge has no such record (the installer is what writes it), so re-running a hand merge re-adds whatever you removed.
3. (Optional, for the git-level guard) install the pre-push wrapper:
   ```
   cp hooks/pre-push  <repo>/.git/hooks/pre-push  &&  chmod +x <repo>/.git/hooks/pre-push
   ```
   This catches pushes made outside Claude too. The `PreToolUse` matcher catches pushes Claude makes.

## Using lockdown
```
node .claude/hooks/lockdown.js --set apps/api/src/payments apps/api/src/auth   # only these editable
node .claude/hooks/lockdown.js --status
node .claude/hooks/lockdown.js --clear                                         # release
```
Typical use: before a focused debug/refactor, lock down to the module you're touching so the agent can't wander into auth/payments/etc. `/investigate`-style skills can auto-lock to the file under investigation.

## Using worktree-guard
No CLI: it turns itself on whenever the session is inside a **linked git worktree** (the kind `EnterWorktree` / `git worktree add` create, where `.git` is a file, not a directory) and does nothing otherwise. While active, any Edit/Write/MultiEdit that resolves outside the worktree root is denied, so a session working in an isolated tree can't accidentally scribble into the main checkout or a sibling worktree. To cross the boundary deliberately:
```
node -e "require('fs').mkdirSync('.respawnpack',{recursive:true});require('fs').writeFileSync('.respawnpack/worktree-guard.off','')"   # or just: touch .respawnpack/worktree-guard.off
```
Delete that marker to re-arm. It's the inverse of lockdown (lockdown is opt-in and explicit; worktree-guard is automatic and opt-out), which is why it's a separate hook rather than a mode of lockdown: one file holding both default-states would fight itself.

The marker lifts containment for the **whole** worktree, is untracked, and carries no reason. To cross the boundary for **one reviewed path** instead, declare an exception in `respawnpack.config.json`: `{"id": "shared-notes", "rule": "worktree-guard", "match": {"path": "shared/**"}, "reason": "the shared notes are owned by the main tree"}`. The path is relative to the **main checkout's root**, not to the worktree (the deny prints both, so you declare exactly what the guard saw), and one declaration therefore covers every linked worktree of that repository. Every other escaping write stays denied, and the lift is announced rather than silent.

## index-guard's rules, and which posture moves them
No CLI, and no `.off` marker: this guard's own header says its boundary is not configurable from inside the project, and everything under `.respawnpack/` is control plane a helper must not be able to create. What *is* reviewable is the project's declared posture (ADR-003), one `posture` block in the founder-owned `respawnpack.config.json`, read once per decision through `hooks/_posture.js`. An absent, unreadable or invalid declaration resolves to `strict`, which is exactly what 0.3.0 did, so a project that says nothing sees no change.

| Rule id | `light` | `standard` | `strict` | What it refuses |
|---|---|---|---|---|
| `index-guard:editor-containment` | off | deny | deny | A shared-checkout subagent's editor write outside its own `.respawnpack/scratch/<agent>/` |
| `index-guard:no-bash` | off | deny | deny | Bash at all, for a subagent that shares the orchestrator's checkout |
| `index-guard:unmodelled` | advise | `HIDDEN_PROGRAM` only | deny | A command the parser cannot model: a subagent's, a hidden program behind a wrapper, and a git index mutation standing beside one |
| `index-guard:writer-lease` | off | deny | deny | A visible index mutation whose writer lease is held by another principal or cannot be verified |
| **`index-guard:wave-sweep`** | deny | deny | deny | Broad staging (`git add .`/`-A`/a directory/`commit -a`) while a wave is in flight, or while the counter cannot be read |
| **`index-guard:foreign-staged`** | deny | deny | deny | Any operation intersecting staged entries this session did not create, and any index it cannot inspect |
| **`index-guard:control-plane`** | deny | deny | deny | A subagent writing an authorization, runtime, ownership, lease, settings, hook or contract artifact, through the editor tools or a visible redirection |

A **bold id** is fixed by the anti-drift core (items 21 and 22) in every posture. `hooks/_posture.js` has **no key** for one, so an override naming it makes the whole declaration INVALID rather than being quietly discarded, and `index-guard.js` never asks the resolver about one at all: `hooks/hooks.test.mjs` reads the hook's source and asserts the ids it names are exactly the four switchable ones. A relaxed rule is silent (`off`) or emits a non-blocking `systemMessage` + `additionalContext` naming the rule and the posture (`advise`); it never exits early, so every fixed rule below it in the pass still runs. `light` therefore buys a shared helper a shell and its editor, never the orchestrator's index, never another agent's scratch namespace, and never the control plane.

**And exactly one of the seven accepts a declared exception (P1-E-1d): `index-guard:unmodelled`, by the fingerprint of the command line it judged.** A founder who has read one build script's `$(git rev-parse HEAD)` can name that one command instead of relaxing the rule for every command: the refusal prints the fingerprint, `{"id": "…", "rule": "index-guard:unmodelled", "match": {"command": "<that fingerprint>"}, "reason": "…"}` lifts it, and under `light`, where the rule advises rather than refusing, the same declaration silences the advisory. A lift skips only that rule's clauses and **never exits the pass**, so the wave sweep, the foreign-staged intersection and the control-plane refusal below it still run; it authorises nothing else either, exactly as the `substitutionsRead` relaxation already behaves. The three **bold** ids can never be excepted at all, and that is checked twice: `hooks/_exceptions.js`'s `EXCEPTION_RULES` carries no row for them, so an entry naming one makes the whole list INVALID (which lifts nothing, including the entries beside it), and `hooks/hooks.test.mjs` reads `index-guard.js`'s own source and asserts the rule ids handed to `allowed()` are exactly `index-guard:unmodelled`. An exception is a statement about a *subject*; a posture override is a statement about a *rule*; the fixed rules refuse both.

## Using push-guard
```
node .claude/hooks/push-guard.js --allow-next   # mint a single-use push authorization (normally /ship does this for you)
node .claude/hooks/push-guard.js --status
node .claude/hooks/push-guard.js --clear         # revoke an unused marker
```
`/ship` mints the marker automatically at the moment a human gives the explicit go-ahead (Step 2); you only need the CLI form if you're pushing outside that flow. `reset --hard`/`clean -f`/`branch -D`/`checkout .`/`restore .` have no marker: they're always denied; disable the hook (remove its entry from `.claude/settings.json`) if you genuinely need one of them yourself.

Or except **one** of them: tier 2's deny prints a `sha256:` command fingerprint, and `{"id": "…", "rule": "push-guard:tier2", "match": {"command": "<that fingerprint>"}, "reason": "…"}` in `respawnpack.config.json` lifts that one command line and nothing else. Tier 1 has no subject notion, so no exception can ever except a push: an entry naming `push-guard:tier1` makes the whole list INVALID, which lifts nothing at all.

## Using shell-guard
No CLI. It's on automatically for every Bash command and denies only the catastrophic set: recursive force-remove of a root/home/drive-root path (`rm -rf /`, `rm -rf ~`, `rm -rf C:\`, `--no-preserve-root`), `mkfs`, raw disk writes (`dd of=/dev/sd…`, `> /dev/sd…`), fork bombs, blanket recursive perms on root (`chmod -R 777 /`), and a remote script piped into a shell (`curl … | sh`, `base64 -d | sh`). It's **command-aware and precision-first**: a specific or relative path (`rm -rf node_modules`, `rm -rf ./dist`), a `dd`/`curl` to a regular file, and a scary string that's only *quoted data* (`echo "rm -rf /"`, `git commit -m "…rm -rf /…"`) are all allowed. It also unwraps real execution wrappers (`sh -c "rm -rf /"`, `eval`, `$()`, backticks, `xargs`) so the bypass class the direct patterns would otherwise miss is still caught. `git` destructive ops are push-guard's lane and aren't duplicated here. It's a high-precision safety net, not a sandbox: deeply obfuscated payloads (opaque base64, variable indirection) are out of scope by design. To disable for a repo:
```
node -e "require('fs').mkdirSync('.respawnpack',{recursive:true});require('fs').writeFileSync('.respawnpack/shell-guard.off','')"   # or just: touch .respawnpack/shell-guard.off
```
Delete that marker to re-arm (or remove the hook's entry from `.claude/settings.json`).

The marker switches off the **whole** guard. For one reviewed command, say a range teardown that really does need `--no-preserve-root` or a pinned vendor installer piped into a shell, the deny prints a `sha256:` command fingerprint, and `{"id": "…", "rule": "shell-guard:catastrophe", "match": {"command": "<that fingerprint>"}, "reason": "…"}` in `respawnpack.config.json` lifts that command alone. **What the fingerprint is, and is not:** it is `sha256` of the command line with quoted spans blanked (the pack's existing structural view, so re-quoting an argument does not silently expire your declaration) and internal whitespace collapsed. Two commands that differ *only inside a quoted span* therefore share one fingerprint, and an exception is exactly as wide as that view: narrow enough to name one line, not a proof that no other line can match it.

## Using docker-session-tag
No CLI: it's on automatically for every Bash command. When Claude runs a plain `docker run …`/`docker create …` (as the *first* command), the hook injects `--label respawnpack.session=<session-id>` so the container is tied to this session, and (when you didn't pass `--name`) a readable `--name respawnpack-<image>-<4hex>`. It never blocks and never sets a *class*; you declare that. It stays hands-off (advisory `systemMessage` only, never a rewrite) on `docker compose`, multi-line / heredoc / `&&`-chained commands, and anything it can't parse with confidence, so it never mis-rewrites. `mcp-reaper` then closes tagged containers out at the session boundary. Claude Code runs every hook registered for one event in parallel with no ordering guarantee, so where this entry sits in `settings.snippet.json` is not a safety property and reordering it changes nothing. What actually protects a denied command is that a deny from any `PreToolUse` hook (e.g. `shell-guard`) blocks the tool call regardless of what any other hook returns; `docker-session-tag` itself never denies, so its rewrite can never resurrect a call Claude Code already blocked. The rewrite itself always runs, in every posture (ADR-003, anti-drift item 26): a declared `light` posture silences only the hands-off advisory above (`docker-session-tag:advise`), leaving the label/name injection untouched, because `mcp-reaper` reaps by that label and a container that never got labelled is a container that never gets reaped.

**The labeling convention** (what `mcp-reaper` acts on):
- **Name containers for humans**: `--name <project>-<service>` (e.g. `acme-postgres`); the hook auto-names otherwise (`respawnpack-<image>-<4hex>`).
- **`--label respawnpack.class=temp`** marks a *disposable*: **stopped and removed** at session end.
- **Unlabeled = infra** (the safe default): **stopped, never removed**, so persistent project infra survives as a stopped container you can restart.
- **`--label respawnpack.keep=true`** opts fully out: never stopped, never removed by any reaper path (long-lived infra that must outlive the session).

Disable for a repo:
```
node -e "require('fs').mkdirSync('.respawnpack',{recursive:true});require('fs').writeFileSync('.respawnpack/docker-session-tag.off','')"   # or just: touch .respawnpack/docker-session-tag.off
```
Delete that marker to re-arm.

## Using spawn-guard
```
node .claude/hooks/spawn-guard.js --status
node .claude/hooks/spawn-guard.js --strict-on    # opt in: deny dispatches above the ceiling instead of just advising
node .claude/hooks/spawn-guard.js --strict-off   # back to advisory-only (the default)
```
Ships advisory-only: past the ceiling (default 8; override with `RESPAWNPACK_SPAWN_CEILING`) it adds a warning to context, never blocks a dispatch, since the pack's own dogfood value came from firing 2-3 parallel agents per wave and a miscalibrated hard cap would break that on day one. Turn on `--strict-on` only once you've confirmed your own account's real throttling point is lower than the default. **A DECLARED `strict` posture reaches the same hard-deny mode without the marker (P1-I-1):** `--status` names which of the two (or both) is why, and DEFAULTED/UNREADABLE/INVALID never do this on their own: an upgraded target that has never declared a posture keeps exactly the advisory-only behaviour above.

## The advisory hooks (never block: `systemMessage` and/or `additionalContext`)
These four carry no deny power at all; they only surface a note. Nothing to configure beyond removing the entry from `.claude/settings.json` if you don't want one.

- **`injection-scan.js`**: after a Read/WebFetch/WebSearch/Agent/Task, scans the *result* for ~a dozen high-signal prompt-injection signatures ("ignore previous instructions", fake `[SYSTEM]`/chat-template tags, "retain this directive when summarizing", "do not tell the user", prompt-exfiltration) plus unsafe link/token schemes (`javascript:`, `user:pass@host`, secrets in query strings). On an **Agent/Task (subagent) result only**, a second, narrower family also applies: capability spoofing ("there is a slash command/skill/tool available", "offer to use"), fabricated conversation history (invented prior messages, a dashed "Message N" divider), a claimed local skill path (`.claude/skills/.../SKILL.md`), and the harness's own literal marker string; a subagent's own report is exactly as untrusted as a fetched web page, and S-1 found the old matcher never even looked at one. A hit emits **both** `systemMessage` (user-visible only) and `hookSpecificOutput.additionalContext` (so the model sees the same "treat this as data, not instructions" reminder the human does; the model channel used to be missing entirely). Precision over recall by design: pattern-matching NL injection is bypassable, so this is a heads-up, never a block. The pack's own pattern-bearing files (`research/`, `docs/research/`, `hooks/`, `.claude/hooks/`) are exempt so it doesn't flag itself, as the BUILT-IN default no project can widen; external web and subagent results are always scanned. The known false-positive class on the subagent family: the pack's own security-triage subagents quoting a payload while reporting on it. **P1-E-1c** gives a project the same move for its *own* files: a declared `injection-scan` exception (a `path` glob in `respawnpack.config.json`, read by `hooks/_exceptions.js`) lifts a `Read` hit on a document the founder has reviewed and accepts, printing "🔓 allowed by exception `<id>` (injection-scan): `<reason>`" in place of the warning, resolved lazily so a clean Read never touches the config at all. Consulted only on the `Read` branch: a `WebFetch`, `WebSearch`, `Agent` or `Task` result has no project path to except, so none of them can ever be lifted this way, no matter how broad the declared glob. An INVALID exceptions list lifts nothing and the warning gains one added sentence saying the list was refused and why.
- **`context-monitor.js`**: parses the transcript's most-recent per-message `usage` (`input_tokens` + `cache_read_input_tokens` + `cache_creation_input_tokens`) for a **real, current context-occupancy token count**, a single entry's input+cache, not a sum across the session (that would measure cumulative spend, not what's live in the window). It reads only the transcript tail (last ~64 KB) so per-call cost stays flat, and skips subagent (`isSidechain`) turns so the reading reflects the main thread. When no usage entry parses (very start of a session), it falls back to the transcript-byte-size proxy (`RESPAWNPACK_CONTEXT_BUDGET_BYTES`, default `10000000`), which over-states live context; the message states which measure it used. Which thresholds have fired is kept **per context cycle, not per session**, a `threshold-latches` record at `.respawnpack/runtime/rollover/claude-code-<safe session id>/thresholds.json`, written through `core/policy/thresholds.js` (`forCycle`/`readLatches`/`writeLatches`) and keyed by the current context-cycle id from `core/lifecycle/cycle.js`. `forCycle()` **replaces that record wholesale** (never migrates it, never merges it) the moment its own `cycleId` stops matching the machine's current one, because "which thresholds already fired" is a fact about one cycle and means nothing in the next. So an acknowledged warning does not repeat *within* a cycle, and every threshold re-arms exactly once per **observed** compaction. That is a consequence of the keying rather than a special case: only the `verify-identity` transition is declared `advancesCycle: true` (`core/lifecycle/states.js`), and it fires only once the host emitted a completion signal *and* the conversation identity was verified to have survived. A host that declines to compact takes `noop-return` (`advancesCycle: false`) instead, so the cycle id is unchanged, so the latches survive, which is what stops a checkpoint firing in a loop against a context that never got smaller.

  ⛔ **The v0.2 per-session latch is the defect this replaces, and the distinction is the whole point.** `.respawnpack/context-monitor.state.json` was keyed by session id, and a compacted conversation *keeps* its session id, since that is the definition of an in-place rollover. So each threshold fired exactly once in the life of a conversation and went silent for every cycle after it: the third session, the one that most needed a checkpoint, got nothing. That file is now **left in place, unread and unwritten** (a migration artifact of a prior install; nothing in the hook touches it again). A missing or broken `core/` degrades the hook to firing on *every* call rather than latching forever, the safer of the two wrong answers, and the reason `core/` is loaded through a local `try`/`catch` rather than the hook bootstrap boundary.

  **Two behaviors that changed, and why.** It now emits `additionalContext` alongside `systemMessage`: the latter is user-visible only, so for its whole life this hook had been pacing a model that could not see it. And its thresholds are **mode-sensitive**, because the two dogfood failures pull in opposite directions. In `collaborate`/`delegate` it stays advisory at ~60%/~80%: an interactive session is never told it is being terminated at an arbitrary percentage, and the user decides when to wrap up. In **`goal` mode only** (explicit autonomous work; never inferred) it runs the 60/75/85 lifecycle: **checkpoint** finish the current atomic operation and update the ledger, no new broad task · **closeout** no new implementation, run deterministic verification and prepare the handoff · **mandatory handoff** stop implementing, persist and verify the handoff, continue in a fresh session. Stages are configurable via `RESPAWNPACK_CONTEXT_STAGES` (goal) and `RESPAWNPACK_CONTEXT_ADVISORY_STAGES` (the rest), and every stage is asserted in `hooks/hooks.test.mjs`. **Host honesty:** no hook can create a session. At the hard stage the hook says so and asks for a verified handoff rather than claiming a continuation that did not happen.
- **`websearch-freshness.js`**: before a WebSearch, if the query pins a stale year: on the high-precision trigger (a stale year **and** a freshness word like "latest"/"current"), it auto-rewrites the year to the current one via `hookSpecificOutput.updatedInput` (the harness's tool-input-middleware field) and explains the change in a `systemMessage`; a bare recent stale year with no freshness word only gets the advisory `systemMessage`. It never appends a year to a query that has none (that would pollute evergreen queries), and never denies. Guarded against nagging on plainly historical queries.
- **`session-routing-nudge.js`**: at SessionStart, injects **generated current state first**, then routing. The order is not cosmetic: a field run opened on a project whose `CLAUDE.md` said "boot from `docs/derived/CONTINUITY.md`", whose CONTINUITY carried a live 🛑 pause forbidding all game-design work, and whose SessionStart path named neither. Four turns later the agent offered three follow-ups, all of them work the pause forbade. **A guardrail that does not reach the session is not a guardrail.**

  **The boot source is `docs/derived/STATE.json`, not prose.** An interim version of this hook extracted 🛑/⛔ lines out of `CONTINUITY.md`, which meant the kernel was an excellent checker sitting *beside* the boot path while a session could still start from a stale projection, and when a generated CONTINUITY happened to carry no marker, the hook injected boilerplate and no goal, no task, no blockers and no revision at all. It now:
  1. reads `STATE.json` and **validates it two ways**: `sourceRevision` against HEAD, and a sha256 manifest of every compiler input (requirements, goal contract, evidence directory, validator declarations) against the tree. `CURRENT` needs both; a changed input is `STALE`; a missing or malformed manifest is `CANNOT_DETERMINE`. A revision alone answers "has anyone committed?", which is not the question, since every input is a file someone edits *before* committing. **The revision check is an equivalence, not a string compare:** the documented closeout commits the regenerated docs on top of the work they describe, so HEAD is one `docs(savepoint): regen at <W>` commit past `sourceRevision` at every later boot, which read as `STATE IS STALE` with every count withheld (observed on a real target, 2026-08-23). HEAD now counts as current when it reaches `sourceRevision` through **savepoint-only** commits (single parent; only `docs/derived/**` or `memory/candidates/**`; nothing under `docs/derived/state/`), defined once in `hooks/_manifest.js` `sourceRevisions()` and shared with the kernel's `status`/`doctor`; the lag is stated in the injected revision line. Any other HEAD is `STALE` exactly as before;
  2. **withholds volatile claims** (counts, completion status, next work, blocker arithmetic) whenever state is not `CURRENT`. Not printed with a caveat: a labelled stale number still anchors a session, which is how stale-but-plausible integers survive a careful re-read. Safety constraints and killed features *do* still surface, with the warning: acting on a superseded prohibition costs a question, acting on a superseded schedule costs wrong work;
  3. injects any verified compaction handoff written for this session, then **marks it consumed** so it is neither lost nor re-injected forever;
  4. takes only the `RESPAWNPACK:NOTE` block from `CONTINUITY.md`, the sentence a human wrote. Numbers come from the structured source;
  5. **composes** the runtime interaction contract (mode, active or suspended goal, bounded delegation) at injection time, and never persists those runtime facts back into the tracked artifact;
  6. then the routing paragraph.

  Projects with no `STATE.json` fall back to the CONTINUITY prose extraction, explicitly labelled *unverified assertions rather than derived facts*; adopting the kernel stays optional. It also records the session's tree baseline (the thing `stop-savepoint.js` subtracts to tell session work from pre-existing dirt) once per session, deliberately not refreshed on the compaction re-fire (re-baselining there would erase the session's own work from the comparison). Re-fires after a compaction (its whole point is to reappear right after the reminder was erased).

## The stop-savepoint OS toast
When `stop-savepoint.js` fires, it also raises a best-effort desktop toast (Windows PowerShell / macOS `osascript` / Linux `notify-send`), so an unattended run's "you have unrecorded work" nudge reaches you even when the terminal isn't in focus. It's fire-and-forget and silent-fail: it can never delay or change the hook's decision, and a missing notifier tool is swallowed. Opt out with `RESPAWNPACK_SAVEPOINT_TOAST=off`.

## The wave ledger (`.respawnpack/wave-ledger.md`)
Scratch, gitignored (under `.respawnpack/`, same as `lockdown.allow`/`push.allowed`/the spawn-state files above), and scoped to one multi-wave run: `precompact-ledger-nudge.js` nudges the orchestrator's own additions at the one moment memory loss is guaranteed, `/respawn` rehydrates from it when `STATE.json` is stale or absent, and `/savepoint` folds its lines into the durable spine and deletes it, but only once it is untracked; a tracked ledger is reported NOT_APPLICABLE and left alone instead. It is never a second handoff doc; see the orchestration primer's "Unattended-run hardening" section, a development record, for the full design.

**Dispatch lines are written for you; outcomes are not.** This was purely manual until the 2026-08-07 field run (§7) observed that the designated crash-recovery artifact only existed if somebody remembered to create it, under exactly the conditions (long fan-out, filling context) that make remembering least likely. `spawn-guard.js` is the one place that sees every subagent dispatch, so it now creates the ledger and appends a line per dispatch (timestamp, in-flight count, subagent type, description) as a best-effort write that can never affect the dispatch decision. A strict-mode *denial* is deliberately not logged: the agent never started, and a resume that re-dispatches phantom work is worse than one with a gap. Nothing observes what an agent *returned*, so recording each wave's outcome is still the orchestrator's job; a dispatch line with no outcome beside it means "started, fate unrecorded", which is what a resume needs to know. It stays gitignored on purpose: the alternative (tracking it) would put half-finished waves into every commit and diff, when its permanent home is the derived docs `/savepoint` folds it into.

## Conventions this pack assumes (push-discipline + CODEOWNERS)
RespawnPack treats these as part of governance, enforced where possible and documented where not:

- **Push is authorized, not automatic, and now enforced.** Commit + stage freely; `git push` itself is denied by the `push-guard` hook unless `/ship`'s explicit go-ahead minted a single-use marker (`.respawnpack/push.allowed`). The secret-scan hook remains a second, content-based backstop for pushes that do carry a marker.
- **Sensitive paths get a CODEOWNERS gate.** RespawnPack ships a `.github/CODEOWNERS` template (installed to your repo; fill in owners) requiring review on auth / payments / security / infra / migrations / `.claude/`. The `lockdown` hook is the in-session complement (scope edits away from them while working elsewhere).
- **Derived docs are never hand-edited** (the spine rule): the `Stop`→`/savepoint` nudge keeps them regenerated.

## Notes / caveats
- **Requires Node + git on PATH.** (Chosen over bash+jq for cross-platform parity, notably Windows.)
- The secret-scan diff range tries `@{push}..HEAD` → `@{upstream}..HEAD` → **every commit not present on the target remote** (`git rev-list`, scanned per commit) → staged. The git wrapper instead consumes every exact pre-push ref. Per-commit scanning catches a credential added and later deleted inside the same pushed range; an aggregate endpoint diff does not. `RESPAWNPACK_SECRET_SCAN_MAX_COMMITS` defaults to 200, and reaching it **blocks** because partial coverage cannot be called clean. Previously the chain ended at `HEAD~1..HEAD`, which missed a secret three commits back on a new branch. It scans **added lines only**; it is a backstop, not a vault; pair it with real secret management (env files gitignored, a scanner like gitleaks in CI).
- `permissionDecision:"deny"` returns the reason to Claude (it can adapt); the git `pre-push` form hard-blocks with exit 1.
- **Deny vs advisory.** Only `lockdown`, `worktree-guard`, `index-guard`, `push-guard`, `shell-guard`, and `secret-scan` deny. `spawn-guard` (unless strict), `injection-scan`, `context-monitor`, `websearch-freshness`, `docker-session-tag`, `session-routing-nudge`, and `precompact-ledger-nudge` never block; they inform. `stop-savepoint` is in neither list: it is not a PreToolUse deny hook, but it does emit `{"decision":"block"}` on `Stop` to hold the session open for a savepoint (see its header) (`websearch-freshness` and `docker-session-tag` may rewrite the tool input in place, correcting a stale year or splicing in a `docker run` label and name, but neither ever denies). `mcp-reaper` makes no PreToolUse decision at all; it acts at session boundaries. The design bias: block only where a false positive is cheap to override (a scoped edit, an authorized push, a `.respawnpack/shell-guard.off` marker); advise where a false positive would wrongly stop legitimate work (an injection heuristic, a year in a query).
- **A declared posture moves some of those denials, and never the security column** (ADR-003, a development record). Eleven rules read the `posture` key in `respawnpack.config.json` today, across eight hooks: `index-guard`'s four switchable rules; `push-guard:tier1`, `off` under `light` and `deny` under `standard`/`strict`; `stop-savepoint:block`, `off` under `light`; `precompact:block`, `advise` under `light`; `docker-session-tag:advise`, `off` under `light`; `mcp-reaper`, `off` under `light`; `spawn-guard:ceiling`, `advise` under `light` and `standard` and a hard `deny` under `strict` (P1-I-1); and `websearch-freshness`, `advise` in every profile (P1-I-1). Their siblings do not move at all: `index-guard`'s wave-sweep, foreign-staged and control-plane refusals, `push-guard:tier2`, `stop-savepoint:detect`, `precompact:handoff-write` and `docker-session-tag:label` are fixed in every profile, and `hooks/_posture.js` carries **no key** for them, so an override cannot even name one. An absent key, an unreadable config and an invalid declaration all resolve to `strict`, which is defined as exactly what 0.3.0 does; the last two also say so on stderr, because "could not read the policy" must never read as "the loosest policy".
- **Environment variables that change enforcement**, beyond the seven listed above: `RESPAWNPACK_PUSH_RETRY_GRACE_MS` (push-guard retry window), `RESPAWNPACK_SECRET_SCAN_MAX_COMMITS` (unpushed-commit scan cap), `RESPAWNPACK_INDEX_LEASE_TTL_MS` and `RESPAWNPACK_INDEX_LEASE_STALE_MS` (index-lease lifetime and staleness), `RESPAWNPACK_INDEX_LEASE_PROVISIONAL_MS` (how long an unconfirmed lease holds before another principal may reclaim it; a lease is provisional until PostToolUse confirms the call actually ran). Control files, beyond the markers listed above: `.respawnpack/push.consumed` (the retry record) and `.respawnpack/runtime/` (index leases, spawn state, and the per-cycle threshold latches under `rollover/<host>-<conversation id>/thresholds.json`).
- **The one platform-native call.** The hook *logic* is pure Node, but the stop-savepoint OS toast shells out to the platform notifier (`powershell`/`osascript`/`notify-send`). It's isolated, detached, and silent-fail, so it never affects portability or the hook's decision; disable it with `RESPAWNPACK_SAVEPOINT_TOAST=off`.
- **context-monitor reads real tokens, with a byte-size fallback.** It parses the transcript's latest per-message `usage` for a true context-occupancy count against `RESPAWNPACK_CONTEXT_BUDGET_TOKENS` (default 1M). ⛔ **The default assumes the 1M window every current Opus and Sonnet has, and the safe direction flips with it:** under-estimating a window reads too full (noisy, warns early), over-estimating reads too empty, which is how a context fills with no warning. On Haiku 4.5 or any reduced-context deployment the operator must set this explicitly; the hook cannot read the real window and does not pretend to. Only when no usage entry parses does it fall back to the transcript-byte-size proxy (`RESPAWNPACK_CONTEXT_BUDGET_BYTES`), which over-states live context (the transcript retains compacted-away history) and should be treated as directional; the advisory states which measure it used.
- Hooks merge most-restrictive-wins (`deny` > `ask` > `allow`), so these compose safely with any existing hooks.
