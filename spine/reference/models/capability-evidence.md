Conventions:
- Each claim carries: source URL; accessed 2026-09-03 (implied for every URL in this file); publication date if the page shows one ("pub: not shown" otherwise); a short verbatim quote or a paraphrase marked (paraphrase).
- "Vendor" = the model maker's own page. "Third-party" = a named external evaluation, leaderboard or publication. "Search snippet only" = a figure seen only in a search-engine summary of a page that was not fetched; treat as UNVERIFIED.
- UNVERIFIED marks anything not confirmed against a fetched page. Do not copy UNVERIFIED items into the register as fact.
- No API keys, tokens or credentials appear in this file, not even as placeholders. Where a doc shows an auth header, only its form is described.
- Benchmarks are reported with the exact name the source used (e.g. "Terminal-Bench 2.1" vs "Terminal-Bench 4.0"); scores from different harnesses/versions are not comparable.

Fable 5 / Mythos 5 (https://www.anthropic.com/news/claude-fable-5-mythos-5, pub June 9, 2026): "Mythos-class models excel at discovering and exploiting software vulnerabilities. They can thus make cyberattacks substantially easier and cheaper to commit." Fetched third-party figure: ExploitBench capture Mythos 5 78.0% vs Opus 4.8 40.0% vs GPT-5.5 34.0% (Vellum, attributed to Anthropic).

Opus 5 (https://www.anthropic.com/news/claude-opus-5, pub July 24, 2026): "Remains behind Mythos 5 on cybersecurity tasks"; the page says the model can find vulnerabilities but classifiers block exploit generation and penetration testing (paraphrase).

Fable 5.1 / Mythos 5.1 (https://www.anthropic.com/claude-fable-and-mythos-5-1, pub September 2026): Fable 5.1 "can now be used to discover software vulnerabilities, though not to develop exploits for them"; cyber safeguards "block 60% fewer false positives than before"; Claude Code users should expect "an average of around 60% fewer interventions per session from our cyber safeguards, relative to the previous safeguards on Fable 5"; Mythos 5.1 "demonstrates the strongest cyber capabilities of any model we've released, though it still falls within the lower category of risk in our Frontier Compliance Framework"; "Claude Mythos 5.1 is identical to Fable 5.1, but it offers more permissive safeguards for vetted individuals and organizations"; access via the "Cyber Verification Program" ("for defensive security work") and the "Life Sciences Verification Program"; "Currently, it is only available to a set of US organizations". Product page https://www.anthropic.com/claude/mythos (pub: not shown): "Our most capable model for cybersecurity and biology research"; the public model can "identify software vulnerabilities in source code" while safeguards prevent "penetration testing, exploit generation, and binary-based vulnerability scanning"; the Cyber Verification Program "provides reduced cyber safeguards for defensive security work"; Glasswing extended to "approximately 150 new organizations in more than fifteen countries" (as of June 2, 2026).

Mythos 5 for defenders (https://claude.com/blog/bringing-claude-mythos-5-to-more-defenders, pub August 21, 2026): "Claude Fable 5 was the first step: it made the model broadly available while blocking dual-use cyber work."; access routes are Project Glasswing, "Claude Security" for Enterprise customers (codebase vulnerability scanning), partner integrations, and the Cyber Verification Program; users of partner tools "would not have a way to prompt the model to, say, develop an exploit for a vulnerability."

API surface of these safeguards (https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback, pub: not shown): "Claude Fable 5.1, Claude Fable 5, and Claude Opus 5 include safety classifiers that can decline a request"; a refusal is HTTP 200 with `stop_reason: "refusal"` and `stop_details.category`; categories: `"cyber"` ("The request could enable cyber harm, such as malware or exploit development. Benign cybersecurity work can also trigger this category."), `"bio"`, `"frontier_llm"`, `"reasoning_extraction"`, `"general_harms"`; `fallbacks: "default"` (beta header `server-side-fallback-2026-07-01`) retries on Anthropic's recommended model per category; "The permitted fallback targets for Claude Fable 5.1 are Claude Opus 4.8 and Claude Opus 5" (https://platform.claude.com/docs/en/models/fable-5-1/whats-new-fable-5-1). Prompting note: "finding vulnerabilities in source code is permitted"; ask "Are there any bugs in this program?" rather than "Does this program compile without errors?"; base64 in tool output can trigger false positives (https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1).

Bottom line supported by the sources: for publicly available Claude models the documented, permitted cyber capability is vulnerability discovery in source code (strongest on the Mythos/Fable line, then Opus 5, then Opus 4.8/4.6); exploit development and penetration testing are classifier-blocked on Fable 5/5.1 and Opus 5 and are available only on Mythos 5/5.1 through Project Glasswing or the Cyber Verification Program. "Opus 4.6 for pentesting" is not a vendor recommendation; the vendor claim for Opus 4.6 is vulnerability finding plus a CyberGym score (66.6%) that Mythos Preview exceeded (83.1%).

## 5. Per-family prompting practice

### 5.1 Anthropic (vendor: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices plus the per-model pages for Fable 5.1, Opus 5 and Sonnet 5; pub: not shown)
1. Be explicit and give the reason: "If you want 'above and beyond' behavior, explicitly request it"; "Providing context or motivation behind your instructions ... can help Claude better understand your goals"; golden rule "Show your prompt to a colleague with minimal context".
2. Structure with XML tags and 3-5 diverse examples: "XML tags help Claude parse complex prompts unambiguously"; "Include 3-5 examples for best results".
3. Long inputs first, question last; ask for quotes: "Put longform data at the top"; "Ground responses in quotes".
4. Steer with `effort`, not `budget_tokens`; adaptive thinking is the mode: "adaptive thinking reliably drives better performance than extended thinking"; on Opus 5/Sonnet 5 thinking is on by default; on Fable 5/5.1 always on; on Opus 5 prefer "thinking enabled at low effort" over disabling it (disabled thinking can leak tool calls as text).
5. Tool use: be imperative ("Change this function" not "Can you suggest"); tone down forcing language ("Use this tool when..." not "CRITICAL: You MUST"); parallel-call instruction boosts to "~100%"; on Fable 5.1 send the batching nudge each turn as a turn-scoped system message; Fable 5.1 rejects forced `tool_choice` ("any"/"tool").
6. Don't over-prompt thoroughness or verification: remove "If in doubt, use [tool]"; on Opus 5 remove "double-check"/"use a subagent to verify" ("cause over-verification"); on Sonnet 5 remove "After every 3 tool calls, summarize progress".
7. Control verbosity explicitly per model: Opus 5 runs long (effort "does not reliably change visible response length"); Fable 5.1 writes fewer updates (ask for them, set `display: "updates"`); tell Claude what to do instead of what not to do; matched prompt style shapes output style.
8. Agentic hygiene: append-only history with thinking blocks passed back unchanged (Fable 5.1 400s on edited prefixes); state in files/git across context windows; "Consider the reversibility and potential impact of your actions" safety block; anti-over-engineering block; "Never speculate about code you have not opened"; subagent damping ("Use subagents when tasks can run in parallel, require isolated context..."; Opus 5 caps via `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`).
Also: no prefill on 4.6+; no non-default `temperature`/`top_p`/`top_k` on Sonnet 5 and Fable 5/5.1; system prompt for role ("Even a single sentence makes a difference").

### 5.2 OpenAI (vendor: https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide ; https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide ; https://developers.openai.com/api/docs/guides/latest-model ; https://developers.openai.com/api/docs/guides/prompt-engineering ; pub: not shown)
1. Set `reasoning.effort` deliberately (GPT-5.6: "none, low, medium, high, xhigh, and max"; "Reserve max for the hardest quality-first workloads"; when migrating, "preserve your current reasoning effort as the baseline, then compare one level lower"); reduce effort to curb "agentic eagerness", raise it and prompt persistence to increase it.
2. Prefer leaner prompts: "configurations with leaner system prompts improved evaluation scores by roughly 10-15%"; "Remove one group of instructions, examples, or tools at a time"; "Expose only tools relevant to the task"; "Don't over-prompt for thoroughness with GPT-5".
3. Avoid contradictory instructions: contradictions make GPT-5 "waste reasoning tokens searching for reconciliation"; define "what level of action each request authorizes"; repeated "ask first" lines "can cause unnecessary approval requests".
4. Use the developer role and section headers: "developer messages are instructions provided by the application developer, prioritized ahead of user messages"; organise as "Identity, Instructions, Examples, Context"; "Markdown headers and lists" and "XML tags can help delineate" sections; put reusable content first for prompt caching.
5. Control output shape with API parameters plus prompt: `text.verbosity` "to set the default level of detail"; GPT-5.6 "more concise by default" so "brevity instructions ... may be unnecessary"; "Use Markdown only where semantically correct"; reapply Markdown rules "every 3-5 messages" if adherence degrades.
6. Reuse reasoning across turns: Responses API `previous_response_id` / "reasoning.context"; explicit prompt-cache breakpoints (GPT-5.6 "prompt_cache_options.mode: explicit"; "cache writes cost 1.25x the uncached input rate").
7. Codex-specific: use OpenAI's exact `apply_patch` tool ("the model has been trained to excel at this diff format"); `shell_command` with `workdir` always set; "Use `multi_tool_use.parallel` to parallelize tool calls and only this"; "default to implementing with reasonable assumptions; do not end on clarifications unless truly blocked"; on Codex-Max/5.3-codex "remove all prompting for the model to communicate an upfront plan, preambles, or status updates during the rollout, as this can cause the model to stop abruptly"; skip the planning tool for "roughly the easiest 25%" of tasks; never `git reset --hard` unless asked; no broad try/catch.
8. Tool preambles on general GPT-5 (non-Codex): "Always begin by rephrasing the user's goal ... provide upfront plans and progress updates" - the opposite of the Codex guidance, so the register must key this on model family.
Note: reasoning models "provide better results on tasks with only high-level guidance"; GPT (non-reasoning) models "benefit from precise instructions that explicitly provide the logic".

### 5.3 MiniMax (vendor: https://platform.minimax.io/docs/token-plan/prompting-best-practices "M-series Usage Tips"; Hugging Face cards; pub: not shown)
1. Explicit task, constraints and output contract: "the task, constraints, and desired output are explicit"; specify "section names, table columns, bullet limits, scope boundaries"; same "colleague with no context" rule as Anthropic.
2. Label sections with bold headers or trailing colons ("Task, Context, Source, Constraints, Output format"); use "named variables" in templates.
3. 3-5 diverse few-shot examples ("usually beat abstract style instructions").
4. Long context: "Placing the task at the end of the prompt has the largest single impact on answer quality"; "Index and delimit source material" with dates and titles.
5. Tools: define each with "name, purpose, inputs, return shape, and failure behavior"; "Use parallel calls for independent read-only lookups. Use sequential calls for workflows" that chain.
6. Reasoning control: deeper reasoning "for planning, debugging, tradeoffs, or long-horizon execution"; skip it for "extraction, rewriting, or formatting"; M3 `thinking` = enabled / adaptive / disabled.
7. Hallucination control: "explicit permission to refuse"; require the model to "quote or cite the source it used".
8. Agentic: "Give the model a small number of active goals at a time"; evaluate prompt changes on the same cases and "record regressions". API-level: recommended sampling `temperature=1.0, top_p=0.95` (M3) plus `top_k=40` (M2.7); on the Anthropic-compatible endpoint "the complete model response must be append[ed] to the conversation history" in tool loops.
Not covered by MiniMax docs: system-prompt structure, temperature per task (docs give only the model-card defaults).

### 5.4 Where the families disagree
- System-prompt structure: Anthropic favours XML tags and a role sentence; OpenAI favours a developer message organised by Markdown headers ("Identity, Instructions, Examples, Context") with XML only for content boundaries; MiniMax favours bold labels / trailing colons. All accept examples wrapped in tags.
- Explicit reasoning instructions: Anthropic - "Prefer general instructions over prescriptive steps" and manage depth with `effort`; manual CoT only when thinking is off (and not on Opus 5). OpenAI - reasoning models want "high-level guidance"; depth via `reasoning.effort`; the Codex guide warns that plan/preamble prompting can make the model "stop abruptly". MiniMax - toggle `thinking` per task class and give few active goals. Net: all three now say "set an effort/thinking knob, do not script the reasoning".
- Progress narration: Anthropic asks you to add narration on Fable 5.1 and trim it on Opus 5; OpenAI's general GPT-5 guide asks for preambles while its Codex guide asks to remove them. Family- and model-specific; cannot be a single default.
- Tool-call formatting: OpenAI prescribes exact tool implementations (`apply_patch`, `shell_command` with `workdir`, `multi_tool_use.parallel`); Anthropic prescribes wording ("Use this tool when...") and per-turn batching nudges, and disallows forced `tool_choice` on Fable 5.1; MiniMax prescribes tool-definition content and asks for full assistant turns to be appended in tool loops.
- Sampling: Anthropic Sonnet 5 / Fable 5.x reject non-default temperature; MiniMax recommends temperature 1.0 / top_p 0.95; OpenAI guides do not mention temperature for GPT-5.x.
- Verification: Anthropic says remove self-check instructions on Opus 5 (over-verification); OpenAI's Codex guide asks the model to "test, and refine"; MiniMax asks for an evaluation loop on the prompt itself. The safe cross-family default is "verify, but do not stack redundant verification instructions".

## 6. General-practice fallback (holds across all three families)

Each item is stated by at least two of the three vendors' guidance pages cited in section 5; the third family's page does not contradict it unless noted.

1. State the task, constraints and the shape of a good answer explicitly; write the prompt so a colleague with no context could follow it. (Anthropic "golden rule"; MiniMax repeats it; OpenAI: precise instructions, no contradictions.)
2. Give the reason behind a constraint, not just the rule. (Anthropic "Add context to improve performance"; MiniMax text-to-speech example is the same pattern; OpenAI "Tell the model when an important ambiguity should trigger a question".)
3. Separate instructions, context, examples and inputs with visible delimiters (XML tags or labelled sections), and keep the layout consistent. (All three.)
4. Provide 3-5 relevant, diverse examples for format- or judgment-sensitive tasks. (Anthropic, MiniMax; OpenAI few-shot "diverse range of possible inputs".)
5. Put long source material first and the question/task last; ask for quotes or citations from the sources. (Anthropic, MiniMax; OpenAI puts reusable content first for caching, which is compatible.)
6. Control reasoning depth with the model's effort/thinking parameter rather than scripting step-by-step reasoning; increase depth for planning, debugging and long-horizon work, decrease it for extraction and formatting. (All three.)
7. Say what to do rather than what not to do, and do not stack contradictory or redundant instructions (thoroughness, verification, "ask first"); remove instructions written for an older model before adding new ones. (Anthropic, OpenAI; MiniMax: evaluate before changing.)
8. Describe tools precisely (name, purpose, inputs, return shape, failure behaviour) and expose only the tools the task needs; instruct the model to call independent tools in parallel and dependent ones sequentially, never guessing parameters. (All three.)
9. In agent loops, keep the conversation history append-only and pass the full assistant turn (including thinking/reasoning items) back unchanged; use the vendor's cache-friendly mechanisms instead of editing earlier turns. (Anthropic Fable 5.1 hard requirement; OpenAI reasoning reuse; MiniMax "complete model response must be append[ed]".)
10. Define the scope and autonomy up front: what the request authorises, which actions need confirmation (destructive, irreversible, shared-system), and that the model should finish the requested work without ending on a question. (Anthropic autonomy and "finish the whole task" blocks; OpenAI Codex "do not end on clarifications unless truly blocked" and action-scope guidance; MiniMax "small number of active goals".)
11. Specify the output contract (length, format, sections, markdown policy) explicitly, because default verbosity and formatting differ per model and change between versions. (All three.)
12. Ground answers: tell the model it may refuse or say it does not know, require it to read/open sources before claiming facts, and ask it to cite what it used. (Anthropic "Never speculate about code you have not opened"; MiniMax "explicit permission to refuse"; OpenAI code-generation guide's read-the-code pattern.)
13. Re-run your own evals when switching model or effort level; effort names are not comparable across models. (Anthropic "match by observed thinking length rather than effort name"; OpenAI "preserve your current reasoning effort as the baseline, then compare"; MiniMax "run the current prompt and the candidate prompt on the same cases".)
